Drawing QA User Guide

How to get the most out of the Controls Drawing QA platform on a real package: preparing the drawings, setting it up for a new project, reading a run, printing the register and marking it up, and keeping findings under control across revisions. The platform does the tedious cross-checking: every tag against its home sheet, every channel against the cable block diagram and the terminations, every placeholder and sheet reference. Your job is the judgement: is each finding real, and what should be done about it. This guide is about making that judgement fast and keeping a clear record of it.

Five habits that matter most

1. Plot every PDF with AutoCAD's PDFSHX set to 1, or the sheet has nothing to read.

2. Read the console warnings and the report's stage table before any finding.

3. Give each package its own output folder and keep the same --exclude setting for it.

4. Close the register in Excel before every run.

5. Mark up every row of the printed register, even the false alarms, with your initials: the marked-up copy is the record of the check.

01The working loop

Using the platform well is a loop, not a one-off run. Each pass leaves fewer open findings, because everything you decide comes back already decided.

02Prepare the drawings

Folder layout

input/<Package>/
├─ PLC/             schematics (PDF)
├─ CableBlocks/     cable block diagrams (PDF)
├─ Terminations/    termination drawings (PDF)
└─ EquipmentList/   optional (listed only for now)
  • Folder names are matched without case and with common aliases (CBD, Terms, EEL). Subfolders inside them are fine.
  • Any folder can be missing. A partial package is still worth checking, and the run says which checks it could not do.
  • Use one input folder per package and revision you want to compare, e.g. input/401002_RevA.

Plot with SHX text

Controls drawings use SHX fonts, which AutoCAD plots as lines. The text is only readable if AutoCAD also stores it as hidden notes in the PDF. That depends on one setting:

PDFSHX = 1      (type PDFSHX at the AutoCAD command line before plotting or publishing)

To check a PDF, open its Comments list in Acrobat or another viewer: it should hold many entries titled AutoCAD SHX Text. A sheet without them is reported as NO_SHX_TEXT and nothing on it is checked. On the 401002 package, 76 of 149 sheets plotted from AutoCAD 2026 had none.

To see how many sheets of a set were plotted without them before a run, use python -m drawing_qa survey --input FOLDER: it lists each folder's SHX-readable, to-decode, scanned and blank sheets in a few seconds, and names the files and the AutoCAD version that plotted them. If a re-plot is not possible, run with --ocr. The tool then learns each letter's strokes from the readable sheets of the same package and decodes the unreadable ones by exact match. Only words whose every letter matched are used; nothing is reported as missing from a decoded sheet; findings that rest on decoded text say (decoded from line work), so check the drawing before acting on them. It needs readable sheets in the same fonts and sizes to learn from; text it has not seen (often much of the title block) stays unread.

Name the files

Name each sheet <drawing>-<sheet>.pdf (401103-036.pdf). The title block is the source of truth, but the file name is the fallback when a title block cannot be read, and DRW-008 flags files whose name and title block disagree. Multi-page PDFs are read too; one page is one sheet.

Leave out what does not belong

  • Merged sets duplicating single sheets are harmless (identical copies are skipped), but they add noise to the input list.
  • Drawings that are known to be out of date are better left out of the run with --exclude (section 4) than removed, so they are still listed.

Before you trust a new package

Spot-check a dozen findings of different rules against the drawings. If one rule is consistently wrong on this package, the cause is usually a setting above or a layout the readers do not recognise (NO_TEMPLATE issues), not the drawings. Fix that first, re-run, then triage.

04Run it

# the usual run: all inputs, outputs to reports/<package folder>/
.venv/Scripts/python -m drawing_qa run --input input/401002

# leave out drawings that are not up to date
.venv/Scripts/python -m drawing_qa run --input input/401002 --exclude term

# choose where the register lives
.venv/Scripts/python -m drawing_qa run --input input/401002 --output reports/401002

Choosing what to include

All four input types are reviewed unless you leave one out with --exclude plc, cbd, term or equip (comma-separated for several).

A left-out type is still listed and its locations still appear in the register, marked "(left out)", but nothing is checked against it and its hops in the traces read "not sourced", never gaps.

One output folder per package

Each run rewrites the register in its output folder. Keep one output folder per package and the same --exclude setting for it, so one run's register can be compared with the last.

Print or save a copy of the register you mark up (e.g. QA_Register_RevA_marked.pdf) before the next run replaces it.

Close QA_Register.xlsx in Excel first. If it is open, the run cannot overwrite it and writes QA_Register-<run id>.xlsx beside it instead; the next successful run files that copy in register_history/.

Then open report.md and look at two tables near the end:

  • Pipeline stages: every stage's note. The rules line says how many rules ran and how many were skipped. A skipped rule did not find nothing; it could not run (for example "Needs TERMINATIONS").
  • Parse issues: NO_TEMPLATE means a sheet's layout was not recognised, so only its identifiers were read. Many of these on one drawing type means the deep checks for that type are not working on this package.

06Triage the register

QA_Register.xlsx is where the work happens: on screen to plan, on paper to mark up. Use its tabs in this order:

  1. Summary: counts by category and severity. Decide where to start: MAJOR findings in the PATH, PLC, TAG and COMP categories are usually the real wiring problems; placeholders are usually one cause for many rows.
  2. Coverage: traced share per area, panel, slot and JB, with anything under 80% shaded. A slot at 0% next to slots at 100% points at one sheet with a systematic problem.
  3. Findings: filter on Rule or Severity and work one rule at a time. The same rule tends to fail the same way, so you get through it faster. Each row gives the location on every drawing type (401103 sh 036 C7, 401310 sh 015 C0) so you can open the sheets side by side.
  4. Tag Index: one row per field device, with the schematic JB beside the CBD route (mismatches shaded red) and where it is drawn on each drawing type. Best for a device-by-device walk through one area.

Read a finding fully

The message says what disagrees, the locations say where, and the recommendation says the likely fix: often the exact tag to use ("did you mean H-TN51W7?").

TAG-003, TAG-005 and COMP-001 often describe one mistake from different sides: a copied tag shows as a duplicate, a gap and a missing home. Mark them up together.

Severity is a starting point

MAJOR: a wiring or identity error that would mislead someone on site. MINOR: incomplete or inconsistent drafting. INFO: a note, such as references to a separate package.

Placeholders are MAJOR on issued sheets (FOR CONSTRUCTION, AS BUILT) and MINOR on preliminary ones.

07Print and mark up

The register has no columns to fill in: it is meant to be printed and marked up by hand. Print the Findings tab (and Tag Index if you walk the package device by device), take it to the drawings, and mark every row.

MarkUse it whenThen
RealIt is a real problem and should be fixedMark up the drawing too, for the drafters
Not a problemThe drawing is right; the platform misread or the rule does not apply hereWrite why, in a few words
LaterYou need information you do not have yet (e.g. the new termination drawings)Check it on the next run
  • Initial and date each page. The marked-up copy is the record of the check; scan or file it with the drawing revision it applies to.
  • Always say why for "not a problem". If the same false alarm comes up on run after run, pass it on (section 10): the platform should be fixed, not the reader.
  • The Ref column (F-0001 …) numbers rows within one run only. Between runs, match a finding by its rule, tag and location, not its Ref.
  • The register is rewritten every run, so anything typed into it is lost. Mark up the paper copy, not the file.

Recording decisions in the file instead

The platform can also keep decisions itself: set enabled = true under [review] in config/project.toml. The register then gets yellow Decision, Checker comment, Reviewed by and Date columns, a No Longer Raised tab and a Waivers tab; decisions are kept in qa_review.sqlite and carried onto the same findings on later runs. It is off by default because the register is marked up on paper.

08Handle patterns, not just rows

When many findings have one cause, deal with the cause once.

Waivers: one rule, many rows (review on only)

Waivers apply only with [review] enabled = true; with review off, mark the group once on the printed copy instead. A known exception that applies to a group (interfaces to another area, a supplier's device range) belongs in config/waivers.toml. Every matching finding is marked WAIVED with the reason, and any decision typed into the register still takes precedence.

[[waiver]]
id = "W-001"
rule = "COMP-002"          # rule ID; * and ? allowed (COMP-*)
subject = "K-TN32*"        # tag / item pattern
reason = "Interface to the RCL package; wired to the PLC there"
approved_by = "DC"
expires = 2027-06-30       # optional: listed but not applied after this date

The Waivers tab of the register shows every waiver, how many findings it matched, and where your own decision overrode it. A waiver that matches nothing is named in the run notes, so stale ones are easy to clear out.

Renames

When a designation has been renamed (AUT renamed to PLC), add "OLD" = "NEW" under [identifiers.superseded] once it is confirmed. Every use of the old name is then reported with the new one as the fix, and traces join up through the rename.

Rules that do not fit a project

In config/rules.toml you can change a rule's severity or turn it off. Prefer marking findings up (or a waiver) over turning a rule off: a disabled rule also stops catching the cases that are real.

[rules."PLACEHOLDER-004"]
severity = "MAJOR"      # report HOLD as MAJOR everywhere

[rules."DRW-010"]
enabled = false         # e.g. a package written in mixed languages

09Across revisions

When the drafters issue corrected drawings:

  1. Replace the PDFs in the package's input folder (or put the new revision in its own folder and run it into the same output folder).
  2. Run with the same --exclude setting as before.
  3. Print the new register and lay it beside the last marked-up copy. A row marked Real that is not on the new register has been fixed: check the fix on the sheet and tick it off.
  4. Rows on the new register that were not on the old one are what the revision introduced. Rows you marked "not a problem" come back each run; mark them the same way.

With [review] enabled = true the platform does this comparison itself: decisions carry over, fixed findings move to the No Longer Raised tab, and First seen shows when each finding first appeared.

10Keep it accurate

The platform is only as good as its checks, and your mark-ups are how it gets better.

  • A false positive that keeps recurring is a platform issue, not a drawing issue. Note the rule and an example (fingerprint, sheet, grid) and pass it on. Confirmed false alarms become AK-N entries in the answer key: tests that make sure they are never reported again.
  • Real problems you confirm on the sample package become AK entries: tests that make sure the platform keeps catching them after every change.
  • Something it missed is the most valuable report of all: it is how new rules are found.
  • Run the test suite after any change to the code: .venv/Scripts/python -m pytest. The answer-key tests need the sample package at input/Main; while it is elsewhere they are skipped, not passed.

12Quick reference

--output FOLDER where the register lives

--exclude term leave a type out (plc, cbd, term, equip)

--include term put back a type the config leaves out

--ocr decode sheets plotted without SHX text

--config FILE another project config
